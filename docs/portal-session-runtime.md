# Portal session runtime contract (M5B, Story 178)

Source direction: PORTAL178-M5B-SESSION-RUNTIME-20261023-01, extending
DESIGN-029 and accepted M3. This document amends M3's token-discard and
UserInfo prohibition for this narrow implementation: retain one short-lived
user access token inside the exact encrypted browser session and query one
fixed HTTPS UserInfo endpoint for current authorization. Never retain a refresh
token, request offline_access, resolve a token by subject, expose credentials in
Principal/templates/errors/logs, or infer operator Human/Client authority.
M3's authentication checks, CSRF and opaque cookie rules continue to apply.

## Store and recovery boundary

Use existing Go BFF and CNPG PostgreSQL, two tables in logical database
`dev_env_v2_portal`, schema `portal`: pending_logins and sessions. Handles are
SHA256 digests only. Rows are created with INSERT only; consumption/revocation use conditional DELETE. Login consumption atomically matches handle, state digest, current
generation and expiry; incorrect state cannot consume the row. Every read is
from the writable primary, never a read replica/cache. Errors, uncertain commits,
outage, expiry, decrypt failure or missing fence deny; there is no memory fallback
or automatic replay. AES-256-GCM uses a separate 32-byte server key; a fresh nonce
and authenticated row/type/version/generation/expiry/state context prevent
ciphertext swaps. Sensitive identity, access token, CSRF, state, nonce and PKCE
fields are encrypted. Polling cannot extend lifetime. The server and cookie
deadline are capped by the actual access-token deadline, with no refresh path.

The shared postgres16 cluster's min/max synchronous replica settings are both
zero. Local synchronous_commit does **not** prove acknowledged-write survival
after promotion. A missing DELETE/revoke or login consumption could resurrect
authority. A generation inside the restored DB, a restart or process-local flag
does not fix this. The M6 source implementation therefore binds the external RecoveryFence to the
actual acquired `pgx.Tx`, measures the exact PostgreSQL incarnation before
session-table SQL, and requires an identical fresh witness snapshot immediately
before and after COMMIT. The [M6 recovery contract](../.agents/reports/portal178-m6/README.md)
specifies the fixed ConfigMap, trusted direct GET, strict record and UID/RV pin.
No observer/controller or cached generation can open admission. Runtime remains 503;
source implementation and disposable protocol evidence do not satisfy live gates.

Existing recovery owner must explicitly close admission before logical restore
into an unchanged server or witness/control-plane restore. Those operations may
preserve all measured PostgreSQL fields and are not automatically detectable.
After recovery, independently rotate both SESSION_AEAD_KEY and SESSION_GENERATION
through the approved server-side secret path. Never restore either old authority
or reuse a generation from backup. Measure the new primary and CAS-open its exact
incarnation; the runtime has no write access to the admission object.

## Concrete provisioning proposal — not granted or applied

Inspect-before-change conventions: existing Authentik ExternalSecret uses
`external-secrets.io/v1`, ClusterSecretStore `onepassword-connect`, target
creationPolicy Owner, engineVersion v2 and item extraction. Its shared
cloudnative-pg superuser fields must **not** be mounted in this BFF. The proposed
portal items are additive; no name conflict appeared in the inspected public
GitOps tree. Live 1Password contents were not inspected.

HaynesKube item `dev-env-v2-portal` retains OIDC_CLIENT_ID/OIDC_CLIENT_SECRET only.
Proposed `dev-env-v2-portal-runtime`: DB_USERNAME, DB_PASSWORD,
SESSION_AEAD_KEY (standard base64 encoding of exactly 32 random bytes),
SESSION_GENERATION (independently held, never restored from DB backup).
Proposed `dev-env-v2-portal-migration`: DB_USERNAME/DB_PASSWORD only. Tom alone
populates these through the supported secure route after review. No key or
credential value is generated by this proposal.

Administrator-reviewed bootstrap SQL (proposal, never run by BFF):

```sql
CREATE ROLE dev_env_v2_portal_migrator LOGIN NOINHERIT NOSUPERUSER
  NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
CREATE ROLE dev_env_v2_portal_runtime LOGIN NOINHERIT NOSUPERUSER
  NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
CREATE DATABASE dev_env_v2_portal;
REVOKE ALL ON DATABASE dev_env_v2_portal FROM PUBLIC;
GRANT CONNECT ON DATABASE dev_env_v2_portal
  TO dev_env_v2_portal_runtime, dev_env_v2_portal_migrator;
-- In dev_env_v2_portal, as administrator:
REVOKE ALL ON SCHEMA public FROM PUBLIC;
CREATE SCHEMA portal AUTHORIZATION dev_env_v2_portal_migrator;
-- Migrator creates ONLY the two tables using migrations/001_sessions.sql.
REVOKE ALL ON SCHEMA portal FROM PUBLIC;
GRANT USAGE ON SCHEMA portal TO dev_env_v2_portal_runtime;
GRANT SELECT, INSERT, DELETE ON portal.pending_logins, portal.sessions
  TO dev_env_v2_portal_runtime;
ALTER ROLE dev_env_v2_portal_runtime IN DATABASE dev_env_v2_portal
  SET search_path = pg_catalog, portal;
ALTER ROLE dev_env_v2_portal_runtime IN DATABASE dev_env_v2_portal
  SET statement_timeout = '5s';
```

Credentials must be set through reviewed secure provisioning, never SQL files,
command arguments or logs. Migrator owns only portal schema/tables, never the
database or other objects; do not grant database CREATE/TEMP or memberships.
Mount migrator only in a separately reviewed migration job. The BFF gets no
migrator/admin token, grant option, inherited/admin role, ownership, UPDATE or CREATE.
Audit effective memberships and default privileges as well as explicit grants.

PUBLIC CONNECT/TEMP on other databases cannot be cancelled by a role-local
REVOKE while PUBLIC retains them. Do **not** revoke shared PUBLIC privileges
across the cluster as a convenience. Proposed role-scoped ordered HBA rules
must precede any broad shared allow; CNPG-generated HBA ordering must be checked
in the eventual review. If that ordering cannot enforce these rejects, this
proposal is insufficient and provisioning remains held:

```text
hostssl dev_env_v2_portal dev_env_v2_portal_runtime  <reviewed-BFF-CIDR> scram-sha-256
hostssl dev_env_v2_portal dev_env_v2_portal_migrator <reviewed-job-CIDR> scram-sha-256
host all dev_env_v2_portal_runtime,dev_env_v2_portal_migrator 0.0.0.0/0 reject
host all dev_env_v2_portal_runtime,dev_env_v2_portal_migrator ::/0 reject
local all dev_env_v2_portal_runtime,dev_env_v2_portal_migrator reject
```

These role-specific rules reject other DBs, plaintext, unmatched source addresses
and local sockets without changing shared users. Positive TLS target-DB and
negative other-DB/plaintext/schema/DDL/membership tests are required before live
approval. Network policy should further narrow BFF/job egress. TLS client must
validate postgres16 CA **and** hostname
`postgres16-rw.database.svc.cluster.local`; `sslmode=require`, skip verification
and fallback plaintext are prohibited. CA reference postgres16-ca and server
certificate postgres16-server are references, not permission to read keys.

## Current authorization and deployment holds

Require pinned issuer+immutable subject, live portal_is_active=true and
portal_is_admin=true, plus the fixed local metadata allowlist. Authentik
2026.8.5 UserInfo evaluates provider profile mappings at request time;
introspection or old ID/access-token claims cannot substitute. The future
provider-local mapping must evaluate active status and direct membership of the
privately pinned existing Admins UUID, preserve normal sub/profile and shared
mappings, and undergo separate haynes-ops review. No UUID is in this document.
Infrastructure PR4246/4257 and actual role/provider acceptance are separately owned.
The source verifier allows only asymmetric signing algorithms; deployed Authentik
must pin the reviewed RSA signer/RS256 and leave JWE encryption disabled. HS256
and unsigned downgrade negatives do not select or provision a provider key.

Request-private session references bind authorization to the exact handle and
token. A second healthy session of the same subject cannot mask a revoked one.
No cached allow. Check before metadata fetch, validate every returned OP ID
against 120/121/122/123/178, then repeat session and live UserInfo authorization
after rendering and immediately before releasing the buffered response. Errors,
redirects, missing/malformed/wrong-typed/duplicate booleans and wrong sub deny.

Local logout needs no IdP. Actual IdP session deletion, disable and token revoke
must deny in live Gate A using disposable identities; cookie disappearance alone
is not immediate token revocation. Do not alter Tom's real Admins membership.
The live metadata adapter remains unavailable: only OP haynes-engineering GET
for the five IDs, and server-validated dev-agents summaries with immutable
catalog dev-env/dev-env, may later be wired. No broad helper token, session-detail
fallback, prompts, logs, streams, downloads, mutation or grants.

Fixed landing route is the dev-env/internal Attention collection. Exact TLS Host
checks remain; forwarded headers cannot establish trust. Future GitOps must use
verified Traefik-to-Go TLS, same-namespace backend, per-backend CA/serverName
ServersTransport and isolation. Shared insecureSkipVerify is forbidden for this
backend. Live IdP, proxy spoof/bypass, HBA, replica promotion, restore and fence
evidence are unrun; source/CI success does not activate this portal.

Login starts have one constant-size per-engine limiter: burst 4, one start/second;
under a two-replica ceiling this is burst 8/two starts per second. The shared store
uses nonblocking insert-only transaction advisory locks across replicas, caps each\nat 256 rows and deletes
at most 32 expired rows per insertion, without UPDATE/admin grants. No function privilege is added: the normal runtime\nrole must prove EXECUTE on the advisory-lock function in disposable/live acceptance.\nA held insert lock never blocks logout/revoke/callback DELETEs, including while\nan insertion waits for its pre-commit witness GET.
These source bounds are conservative admission limits, not measured production
capacity or an SLO; deployment replicas, retention policy, real API latency and
legitimate-flow proof must be accepted before activation.

A successful store operation requires three fresh admission GETs. Current handler
composition makes seven protected store reads (21 GETs) and two current UserInfo
calls per Attention response; the hosted fixture asserts that exact count and
reports serial GET/full-request latency. There is no automatic background polling,
retry or cached allow. Two in-flight GETs per fence and two SQL connections per
pool bound concurrency. Keep automatic browser polling disabled until live API
budget evidence supports a frequency and replica/client ceiling. Loopback fixture
latency cannot establish a live control-plane load budget.
