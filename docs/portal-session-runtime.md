# Portal session runtime contract (M5B, Story 178)

Source direction: PORTAL178-M5B-SESSION-RUNTIME-20261023-01, extending
DESIGN-029 and accepted M3. This document amends M3's token-discard and
UserInfo prohibition for this narrow implementation: retain one short-lived
user access token inside the exact encrypted browser session and query one
fixed HTTPS UserInfo endpoint for current authorization. Never retain a refresh
token, request offline_access, resolve a token by subject, expose credentials in
Principal/templates/errors/logs, or infer operator Human/Client authority.
M3's authentication checks, CSRF and opaque cookie rules continue to apply.

## Store and recovery boundary

Use existing Go BFF and CNPG PostgreSQL, two tables in logical database
`dev_env_v2_portal`, schema `portal`: pending_logins and sessions. Handles are
SHA256 digests only. Rows are created with INSERT only; consumption/revocation use conditional DELETE. Login consumption atomically matches handle, state digest, current
generation and expiry; incorrect state cannot consume the row. Every read is
from the writable primary, never a read replica/cache. Errors, uncertain commits,
outage, expiry or decrypt failure deny; there is no memory fallback
or automatic replay. AES-256-GCM uses a separate 32-byte server key; a fresh nonce
and authenticated row/type/version/generation/expiry/state context prevent
ciphertext swaps. Sensitive identity, access token, CSRF, state, nonce and PKCE
fields are encrypted. Polling cannot extend lifetime. The server and cookie
deadline are capped by the actual access-token deadline, with no refresh path.

**Recovery witness dropped, 2026-10-26.** Tom ruled on #178 that a PostgreSQL
restart or failover must need no human action. The portal no longer reads the
`dev-env-v2-portal-admission` ConfigMap, measures the backend incarnation, or
reads any admission input. A store transaction is `SET LOCAL synchronous_commit
= on`, the session SQL, then one COMMIT; an uncertain commit is still unavailable
and never replayed. The shared postgres16 cluster has no synchronous replica, so
an acknowledged revoke can be lost by failover or by a restore from backup, and
the revoked session then authenticates again until it expires (at most the 12h
absolute TTL). That risk is accepted. To end it, delete the session rows or
rotate `SESSION_GENERATION`; every row carries the generation in its SQL key and
AEAD context, so rotation invalidates every existing session and pending login.
DESIGN-029 records the ruling; the M6 recovery contract is superseded.

## Local Pages source check

`dev-env-portal pages-source-check` is a local process diagnostic. It reads only
the existing `/etc/dev-env-portal/config/pages-alertmanager.json` configuration
and, when enabled and valid, performs the same fixed Alertmanager snapshot GET
as the Pages adapter. It accepts no arguments, flags or source overrides. It
does not start the web server, initialize OIDC or connect to the database.

Output is one bounded JSON object with `status`, `count` and `observedAt`.
`status` is `available`, `disabled` or `unavailable`. Only `available` includes
a numeric count (including a real zero) and the successful read's observation
time. Other states use JSON null for both fields, meaning Unknown. Disabled or
malformed configuration makes no source request. Source failures have no stale
fallback. Alert content, source URLs and upstream error details are never output.
Exit 0 means available; exit 1 means disabled or unavailable; exit 2 means invalid
command usage. Usage errors print only `portal usage unavailable` to stderr.

The command retains the existing fixed URL, five-second timeout, response bound,
no-proxy/no-redirect policy and no retry. It adds no HTTP endpoint or access
permission. Running it against an installed portal still requires separately
authorized process/exec access; a successful check proves neither browser OIDC
authorization nor human UI acceptance. Existing Pages route authorization is
unchanged.

## Current authorization and deployment holds

Require the pinned issuer, a live UserInfo response for the session's own
subject with portal_is_active=true and portal_is_admin=true, plus the fixed
local metadata allowlist. Access is by group membership, not by a pinned
subject (Tom, 2026-10-26; DESIGN-029 "Group-based access"). Authentik
2026.8.5 UserInfo evaluates provider profile mappings at request time;
introspection or old ID/access-token claims cannot substitute. The future
provider-local mapping must evaluate active status and direct membership of the
privately pinned existing Admins UUID, preserve normal sub/profile and shared
mappings, and undergo separate haynes-ops review. No UUID is in this document.
Infrastructure PR4246/4257 and actual role/provider acceptance are separately owned.
The source verifier allows only asymmetric signing algorithms; deployed Authentik
must pin the reviewed RSA signer/RS256 and leave JWE encryption disabled. HS256
and unsigned downgrade negatives do not select or provision a provider key.

Request-private session references bind authorization to the exact handle and
token. A second healthy session of the same subject cannot mask a revoked one.
No cached allow. Check before metadata fetch, validate every returned OP ID
against 120/121/122/123/178, then repeat session and live UserInfo authorization
after rendering and immediately before releasing the buffered response. Errors,
redirects, missing/malformed/wrong-typed/duplicate booleans and wrong sub deny.

Local logout needs no IdP. The code client accepts only `/application/o/token/`
on the configured issuer host, the Authentik 2026.8 token endpoint. Issuer HTTP
configuration rejects any allowlisted path with a `revoke` or `introspect`
segment. No revoke, introspection, refresh, or end-session call is added, and
logout stays a local durable DELETE. Adding `end-session` to that reject list
remains optional and is not part of this source; no new IdP call is introduced.
This pin is source configuration, not a
live provider request or a shared Authentik change. Actual IdP session deletion, disable and token revoke
must deny in live Gate A using disposable identities; cookie disappearance alone
is not immediate token revocation. Do not alter Tom's real Admins membership.
The live metadata adapter remains unavailable: only OP haynes-engineering GET
for the five IDs, and server-validated dev-agents summaries with immutable
catalog dev-env/dev-env, may later be wired. No broad helper token, session-detail
fallback, prompts, logs, streams, downloads, mutation or grants.

Fixed landing route is the dev-env/internal Attention collection. Exact TLS Host
checks remain; forwarded headers cannot establish trust. Future GitOps must use
verified Traefik-to-Go TLS, same-namespace backend, per-backend CA/serverName
ServersTransport and isolation. Shared insecureSkipVerify is forbidden for this
backend. Live IdP, proxy spoof/bypass, HBA, replica promotion and restore
evidence are unrun; source/CI success does not activate this portal.

## Default-off portal action source configuration

Source may optionally read `config/session-actions.json` under the existing
portal root. Absence leaves send and private history disabled. The object may
contain `send` and/or `history`; each names only resources: exactly one key,
`targets`, a nonempty array (at most 64) of `{ "name", "uid" }`. The file
names no person: there is no `issuer` or `subject`. Any principal that the
existing group authorizer admits (a current portal session and live UserInfo
with `portal_is_active` and `portal_is_admin` both true) may use a configured
action, and each request is checked for its own authenticated principal. The
issuer stays pinned by the session verifier, not by this file. Invalid,
duplicate, ambiguous or unknown fields, a bad target, and duplicate target
names or UIDs fail closed. This scope is additional to current session,
UserInfo and group authorization; metadata access does not grant either
action. The existing operator token and pinned CA are reused. Do not populate
this file with real targets without separate authorization. See DESIGN-029
"Group-based action scopes, 2026-10-29".

**Old-format or malformed files stop the portal at startup.** A file that
carries `issuer` or `subject` (the former per-person format), or is otherwise
malformed, is refused as a whole at load: no action scope is returned and
`LoadProduction` fails, so the portal process exits. There is no compatibility
fallback. In a rollout the new pod crash-loops and never becomes ready;
`maxUnavailable: 0` keeps the old pod serving. The portal reads the action file
only at startup. A broken file followed by an unrelated restart, such as a
node drain or eviction, takes the portal down until the file is fixed.
Change the file only together with, or after, the portal image that accepts
it: an older image refuses the targets-only format the same way.

Operator source separately accepts repeatable `--portal-send-target=name=uid`
and `--portal-history-target=name=uid` options. These flags stay the
per-target-session allowlist (the agent sessions that may be messaged or whose
history may be read): the portal file grants no operator target outside them.
Each action has its own target map; neither is enabled by `--enable-portal-reader` alone. Explicit targets
require that reader flag, and invalid or duplicate entries fail startup. These
source interfaces are not an installation or approval: deployment, eligible
idle agentd rollout, provider format qualification, live private access and
send proof remain separate prerequisites. Legacy unbound history and agentd
versions lacking the conversation control remain unavailable.

## Pilot agent image for one session (default off)

History binds only at a session's first launch on agentd 2.47 or later, and
every pod today runs the one templates image. A templates edit drains every
idle session. To try a newer agent image on a new session without that, the
operator takes two flags. Both are empty by default, and both or neither must
be set:

- `--pilot-agent-image` is `ghcr.io/thaynes43/dev-env:2.X.Y@sha256:<64
  lowercase hex>`. The 2.x tag and the digest are both required. The operator
  checks syntax only. The signature is checked by the publish workflow's
  cosign verify, by review of the HelmRelease line, and by the cluster's image
  audit.
- `--pilot-agent-session` is `<parent>/<key>`. The parent is the creating
  session's name, a DNS-1123 label such as `dev-env-1027-111645`: a session
  caller's `spec.parent` is its own session name. Human, client, coordinator,
  portal and standby callers record `<namespace>/<name>` parents, which this
  flag cannot select. The key is a non-empty label value. There is exactly one
  `/`.

A set pair with a bad value, or only one flag, fails operator startup.

A session runs on the pilot image when all of these hold:

- Its `spec.parent` equals the parent. The API sets that from the caller's
  authenticated identity, so only that session can create such a session.
- Its idempotency-key label equals the key. The caller sets that with
  `agent-run --idempotency-key`.
- The agent is Claude in remote or local mode, or Codex in remote mode; the repo is `dev-env`. Codex local and task sessions are excluded.
- It has no workspace, no project canary and no private pilot.

The selection is not limited to one session. While the flags stay set, it
matches every session with that parent and key, for the life of each one. The
API dedupes a key only against unfinished sessions, so the same parent can
create a second matching session after the first is suspended or finished. A
session that already had that parent and key before the flags were set gets
the pilot image at its next pod. Keeping it to one session is a procedure, not
something the operator enforces:

- Choose a key that parent has never used.
- Use it for one session only; the key is a procedural one-use choice, not a lifetime enforcement mechanism.
- Remove or change the flags when the pilot ends through the separately approved operator configuration procedure.

Only the image of a matching session's own pod changes. The pod keeps
everything else: the templates revision label, env, args, mounts, profile,
Secrets, egress and grants. Hold pods and task-budget workers keep the
templates image. With the flags unset, every pod is built exactly as before.
The operator log line "created the session pod" names the pod's agent image,
so a match is visible there.

What this means in use:

- History needs the session's first launch to be on the pilot image. Create
  the session after the flags are set. An existing session is never rebound.
  A session that first launched on an older agentd stays without history,
  even if a later pod runs the pilot image.
- The pod carries the current templates revision. It drains only on a
  templates change, and its next pod is on the pilot image again while the
  flags stay.
- Removing the flags puts a matching session's next pod on the templates
  image. Its history is then Unavailable if the templates image predates 2.47.

Trust model: the image is pinned by digest, from the same signed repository
as the templates image, and the flags are a reviewed HelmRelease line. The
pilot changes the code version of the matching sessions. It does not change
their profile, Secrets, egress or grants. The flags select by metadata and are
not an authorization to read history or account allowance, or evidence of native
process ownership; the applicable action scope is still required. Interactive
sessions do not acquire an automatic TTL from this selector.

### Separate Codex remote pilot image (default off; source only)

`--remote-pilot-agent-session='<parent>|<key>'` and
`--remote-pilot-agent-image=ghcr.io/thaynes43/dev-env@sha256:<64 lowercase hex>`
are a separate pair. Both must be set or both unset; malformed values fail
operator startup. A `:2.X.Y` release tag may precede the required digest;
tag-only image references are refused. The parent is either a DNS-1123 session
name or `<namespace>/<serviceaccount>`, such as `dev/dev-env`. The namespace is
a DNS-1123 label and the ServiceAccount name a DNS-1123 subdomain. The key is
a non-empty Kubernetes label value. Neither parent form nor a label value can
contain `|`, so exactly one `|` separates the parent from the key. Quote the
session argument in a shell.

The pair selects only an ordinary Codex remote session in `dev-env` whose
`spec.parent` and idempotency-key label both match exactly. Workspace, project
canary, private pilot and task-budget sessions are excluded. Only the image of
its newly built, owned session pod changes. The original-HOME `home-verify`
init container uses that selected image too. Hold pods, existing pods and
unmatched pods stay unchanged; unset flags preserve the existing pod bytes.

The existing `--pilot-agent-*` and `--task-pilot-agent-*` pairs remain
independent. Startup refuses a remote tuple with the same parent AND key as
either existing pair, regardless of flag order. Legacy precedence in the pod
builder remains only as defense in depth; flag configuration cannot reach it.
Task and remote modes cannot match both task and remote selectors.
Before separately approved activation, verify that the remote tuple identifies
one session and do not reuse it: the selector does not reserve a key or enforce
lifetime uniqueness. This source change activates no flags and grants no
runtime, lifecycle, access or enrollment authority.

## Default-off portal launch route

The operator can let the portal reader start one constrained agent session on
behalf of a portal user. It is off unless `--portal-launch-repo=<repo>` is set.
Three flags configure it:

- `--portal-launch-repo=<repo>`: repeatable (at most 16, no duplicates), each a
  repository name as the AgentSession schema accepts.
- `--portal-launch-profile=<name>`: required whenever a repo is set. A DNS-1123
  label, it is the templates profile every launched session runs on.
- `--portal-launch-max-unfinished=<n>`: 1 to 8, default 2. The most unfinished
  portal-launched sessions at once.

Any of them needs `--enable-portal-reader`, and the profile and cap flags need
at least one repo; a missing or invalid value fails startup. With no repo flag
the route does not exist: `POST /v1/portal/sessions` answers 404, and the portal
reader still cannot create through `POST /v1/sessions`.

- **Route.** `POST /v1/portal/sessions`, for the portal reader only. Every other
  caller, including a human, a client, a session and a coordinator, is refused.
- **Request.** Strict JSON: unknown keys, duplicate keys, JSON `null` for any key,
  trailing values and a query string are refused. Fields are `requestID` and
  `actorRef` (the same opaque-ID rule as Send), `repo` (in the allowlist), `mode`
  (`task`, `local` or `remote`), `model` (a full id; an alias such as `opus` is
  refused by the rule agent-run uses), and optional `effort` and `size` (`S` or
  `M`). A task needs a `prompt`; local and remote take none. The agent is always
  `claude`.
- **What it can never set.** Project, base, profile, tools, limits, lifecycle,
  restore, canary, name and lane are not fields. The profile is the operator's
  flag.
- **One create path.** The route builds a fixed `CreateSessionRequest` and runs
  it through the same create handler as `POST /v1/sessions`, so the model,
  effort, size, prompt, profile and idempotency rules are the existing ones. It
  writes no second validator. A prompt that fits the 64 KiB limit but whose
  session document would exceed agentd's 128 KiB transport (for example 50,000
  `<` characters) is refused by that existing check with 422.
- **Parent.** `spec.parent` is `portal/<actorRef>`, which the portal shows as
  "launched by". The caller is a derived value that exists only inside this
  route: depth 1, no profile to hand on, and no other route accepts it. A parent
  equal to another configured caller's identity is refused.
- **Cap.** Inside the create lock (which is per operator replica, so launches
  racing on two replicas can exceed the cap by one each), after the
  idempotent-repeat check, the route counts the unfinished sessions (the predicate the idempotency dedupe uses) whose
  parent starts with `portal/`. At the cap it answers 429 `limit_exceeded` and
  creates nothing. The cap is across all portal users, not per user. A repeat of
  an existing request still returns its session at the cap, and a finished or
  suspended session no longer counts.
- **Idempotency.** The key is `portal-` plus 40 hex digits of the request ID's
  SHA-256. The existing per-parent dedupe applies: a repeat of the same request
  while the session is unfinished returns the same session (200), the same ID with
  a different request is a conflict (409), and a new ID starts a new session. Once
  that session has finished, the same ID starts a new one.
- **Receipt.** `requestID`, `sessionName`, `sessionUID`, `phase` and `observedAt`.
  `Pending` is expected. Errors use the existing shapes and never echo the prompt.

### Choosing the profile is Tom's activation decision

What a launched session can reach is exactly what its profile grants. The
templates' default profile, `full`, is the widest: the GitHub bot token, GCP,
Cloudflare, Proxmox-reader and Omni keys, the MCP secrets (including the UniFi
write tools), and the Claude and Codex logins. The route therefore never falls
back to it: the flag is required. For a task that runs on a portal user's
prompt, activation should name a narrower profile, such as `dev`, and Tom
confirms what that profile grants before the flag is set. `dev` still carries
the GitHub bot token and the UniFi MCP token, and it has no keeper Claude login,
so a remote launch on `dev` shows Login required until someone runs
`agent-run login`. The operator refuses `workbench` at startup, and on every request the route
resolves the profile and refuses one that names any ServiceAccount (the
workbench's carries exec rights) or that the templates no longer hold. A templates edit to
that profile changes what portal launches get, from the next pod each one
starts.

### Activation delta (not applied)

Three operator flags, `--portal-launch-repo`, `--portal-launch-profile` and
`--portal-launch-max-unfinished`, plus a `launch` scope in the portal's private
action file (`session-actions.json`), bound to repositories only (see
"Default-off portal launch form (BFF)"). Any principal the group check admits
may launch. The profile choice and every live flag need Tom's confirmation.

## Default-off portal launch form (BFF)

The portal can show a New agent form on the Sessions page and post it to the
operator's launch route (see "Default-off portal launch route"). It is off unless
the private action file `config/session-actions.json` has a `launch` entry, and
the operator has the launch flags. The portal reads the file once at start.

**The `launch` scope.** An optional top-level entry beside `send` and `history`,
parsed as strictly as they are. It has exactly one key, `repos`: a non-empty
list of at most 16 distinct repository names. There is no `issuer` or `subject`;
any principal the group check admits may launch. Any other key, shape or value,
including the former `issuer` and `subject` keys, makes the portal process exit
at startup. In a rollout the new pod crash-loops and never becomes ready;
`maxUnavailable: 0` keeps the old pod serving. The startup-only read also means
a broken file followed by a node drain, eviction or other unrelated restart
takes the portal down until the file is fixed. Change the file only together
with, or after, the portal image that accepts it. With no `launch` entry the
route and the form do not exist, and `send` and `history` behave as before.

```json
{"launch": {"repos": ["dev-env"]}}
```

**The route.** `POST /portal/projects/dev-env/environments/internal/session-launches`
only. It makes the same checks as Send, by the same code: a current portal
session, the exact Origin, a form content type, the session's CSRF value, a fresh
authorization for dev-env for the request's own principal. It also needs a
43-character request ID, a repository in the scope, a mode of `task`, `local` or
`remote`, a model from the offered list of full Claude ids, an effort and size
from their fixed sets, and no other form key. Anything else is denied and nothing
goes to the operator. The one exception is the prompt rule: a task without a
prompt, or a local or remote launch with one, answers with a result page naming
the field.

**What it sends.** One `PortalLaunchRequest` to the operator, with the actor
reference Send uses (a keyed hash of the portal session and principal). The
prompt is not logged, stored or echoed, and no reservation is kept: the request
ID becomes the operator's idempotency key, so a resubmitted form returns the same
session while that session is unfinished. Each portal pod runs one dispatch at a time
(one lock around the fresh authorization check and the operator call), so two
concurrent sends of one form reach the operator one after the other and the
operator returns the same session to the second. A prompt over 64 KiB of UTF-8
bytes gets a result page with a field error, not a denial.

**What the user sees.**

- Created or existing: a 303 to the Sessions page with the new agent selected.
  That page is the receipt: name, UID, phase (Pending means the pod is starting)
  and the Remote Control line.
- Too many portal launches running (429), the operator's refusal or missing route
  (403, 401, 404), a field it refused (400 or 422), a request ID that already
  started a session with different details (409) and an unknown outcome each get
  a result page with fixed wording. Unknown means the request was sent and no usable answer
  came back, so a session may or may not exist. The page says to check the Agents
  list; it never retries.

The Sessions page carries the form for any principal the group check admits,
and only when the route is configured. The page then has the send policy (`form-action 'self'`),
still with no script. The Tasks page never has it.

**Activation (not applied).** The operator needs `--portal-launch-repo`,
`--portal-launch-profile` and `--portal-launch-max-unfinished`; the portal needs
this `launch` scope in its private file, after the portal image is updated; and
Tom confirms the repositories and the profile. This change enables none of them.

## Usage navigation and Sessions read diagnostics (#241)

Usage has a canonical view URL, `sessions?view=usage`, with its own active top
and mobile navigation item. It shows usage without the session rail or list;
refresh and browser history preserve that view. Pages shares the product
navigation. Usage rows select Sessions by stable session UID, so activity-based
reordering cannot change their target. Other query combinations remain refused.

Sessions reads must finish by request start plus 12 seconds, including time
already spent on initial authentication and authorization. The same deadline
covers credentials, up to ten operator pages, projection and selected history;
each operator HTTP request still has its five-second timeout. This leaves
headroom within the 20-second write timeout. Final authentication,
authorization and form checks share a deadline of request start plus 19 seconds
(or the request's earlier deadline), leaving time for rendering. If initial
checks exhaust the read budget, the source read is skipped: `read_not_started`
is distinct from an operator timeout, and no credential or operator read runs.
A read stopped at the ten-page cap is a successful but incomplete read (`complete=false`); it updates the last-success
time and emits no failure event. Failures show a fixed reason (not connected,
credential unavailable, operator unreachable/timed out, HTTP refusal, contract
refusal, clock ahead or cancelled), the observation time, Retry at the same canonical
URL, and the last successful read time if this process has one. Contract
positions use one-based pages and zero-based row indices; a page-level failure
has no row. No partial or cached session data is shown after a failed read.

One structured `portal_session_read_failed` line records each failed read:
`reason_code`, `page` (0 outside an inventory-page read), `row_index` (-1 without a row),
`http_status` (0 without a response), `timed_out`, `elapsed_ms` (including initial
checks), `pre_read_ms` (time before the source read) and phase
measurements `credential_ms`, `fetch_ms`, `decode_ms`, `projection_ms`, `history_ms`. It includes
no upstream errors, values, headers or credentials. `not_connected` and
`cancelled` log at Info; other failures log at Warn. A deadline reached between
pages reports page 0 because no inventory page was requested. A failed Sessions
read keeps a separately configured New agent form available. Page, session and
last-activity observation timestamps up to two seconds ahead are clamped to
the portal's now; anything further ahead is refused. Empty, stale and unavailable
retain their separate meanings; a pending HTTP read shows no invented empty result or zero.

## Tasks list truth (#253)

A task detail always shows Execution owner and Accountable owner, each as recorded or "Not recorded". The list keeps the short owner and shows "Owner not recorded" when both are empty. The next action is one line from the status alone: "Waiting for approval", "Waiting for an answer", "Paused: resume needs its owner", or "On hold". In progress and every other status have no next action. The detail shows "Last updated" with the age and the UTC time. A work package is a fixture only when its raw description starts with one of three exact prefixes: "Synthetic fixture", "Synthetic acceptance fixture" or "Negative authorization probe". The match is case-sensitive, the description is not trimmed, and the subject is never read. A fixture gets a Fixture badge and is listed under "Fixtures (synthetic)" after the real groups. It stays visible and is omitted from Needs attention, including that rail count. A Needs attention task's detail opens with the Needs attention panel: the status once, as the reason, then the next action when there is one. Unknown stays Unknown.
