# Portal session runtime contract (M5B, Story 178)

Source direction: PORTAL178-M5B-SESSION-RUNTIME-20261023-01, extending
DESIGN-029 and accepted M3. This document amends M3's token-discard and
UserInfo prohibition for this narrow implementation: retain one short-lived
user access token inside the exact encrypted browser session and query one
fixed HTTPS UserInfo endpoint for current authorization. Never retain a refresh
token, request offline_access, resolve a token by subject, expose credentials in
Principal/templates/errors/logs, or infer operator Human/Client authority.
M3's authentication checks, CSRF and opaque cookie rules continue to apply.

## Store and recovery boundary

Use existing Go BFF and CNPG PostgreSQL, two tables in logical database
`dev_env_v2_portal`, schema `portal`: pending_logins and sessions. Handles are
SHA256 digests only. Rows are created with INSERT only; consumption/revocation use conditional DELETE. Login consumption atomically matches handle, state digest, current
generation and expiry; incorrect state cannot consume the row. Every read is
from the writable primary, never a read replica/cache. Errors, uncertain commits,
outage, expiry or decrypt failure deny; there is no memory fallback
or automatic replay. AES-256-GCM uses a separate 32-byte server key; a fresh nonce
and authenticated row/type/version/generation/expiry/state context prevent
ciphertext swaps. Sensitive identity, access token, CSRF, state, nonce and PKCE
fields are encrypted. Polling cannot extend lifetime. The server and cookie
deadline are capped by the actual access-token deadline, with no refresh path.

**Recovery witness dropped, 2026-10-26.** Tom ruled on #178 that a PostgreSQL
restart or failover must need no human action. The portal no longer reads the
`dev-env-v2-portal-admission` ConfigMap, measures the backend incarnation, or
reads any admission input. A store transaction is `SET LOCAL synchronous_commit
= on`, the session SQL, then one COMMIT; an uncertain commit is still unavailable
and never replayed. The shared postgres16 cluster has no synchronous replica, so
an acknowledged revoke can be lost by failover or by a restore from backup, and
the revoked session then authenticates again until it expires (at most the 12h
absolute TTL). That risk is accepted. To end it, delete the session rows or
rotate `SESSION_GENERATION`; every row carries the generation in its SQL key and
AEAD context, so rotation invalidates every existing session and pending login.
DESIGN-029 records the ruling; the M6 recovery contract is superseded.

## Current authorization and deployment holds

Require the pinned issuer, a live UserInfo response for the session's own
subject with portal_is_active=true and portal_is_admin=true, plus the fixed
local metadata allowlist. Access is by group membership, not by a pinned
subject (Tom, 2026-10-26; DESIGN-029 "Group-based access"). Authentik
2026.8.5 UserInfo evaluates provider profile mappings at request time;
introspection or old ID/access-token claims cannot substitute. The future
provider-local mapping must evaluate active status and direct membership of the
privately pinned existing Admins UUID, preserve normal sub/profile and shared
mappings, and undergo separate haynes-ops review. No UUID is in this document.
Infrastructure PR4246/4257 and actual role/provider acceptance are separately owned.
The source verifier allows only asymmetric signing algorithms; deployed Authentik
must pin the reviewed RSA signer/RS256 and leave JWE encryption disabled. HS256
and unsigned downgrade negatives do not select or provision a provider key.

Request-private session references bind authorization to the exact handle and
token. A second healthy session of the same subject cannot mask a revoked one.
No cached allow. Check before metadata fetch, validate every returned OP ID
against 120/121/122/123/178, then repeat session and live UserInfo authorization
after rendering and immediately before releasing the buffered response. Errors,
redirects, missing/malformed/wrong-typed/duplicate booleans and wrong sub deny.

Local logout needs no IdP. The code client accepts only `/application/o/token/`
on the configured issuer host, the Authentik 2026.8 token endpoint. Issuer HTTP
configuration rejects any allowlisted path with a `revoke` or `introspect`
segment. No revoke, introspection, refresh, or end-session call is added, and
logout stays a local durable DELETE. Adding `end-session` to that reject list
remains optional and is not part of this source; no new IdP call is introduced.
This pin is source configuration, not a
live provider request or a shared Authentik change. Actual IdP session deletion, disable and token revoke
must deny in live Gate A using disposable identities; cookie disappearance alone
is not immediate token revocation. Do not alter Tom's real Admins membership.
The live metadata adapter remains unavailable: only OP haynes-engineering GET
for the five IDs, and server-validated dev-agents summaries with immutable
catalog dev-env/dev-env, may later be wired. No broad helper token, session-detail
fallback, prompts, logs, streams, downloads, mutation or grants.

Fixed landing route is the dev-env/internal Attention collection. Exact TLS Host
checks remain; forwarded headers cannot establish trust. Future GitOps must use
verified Traefik-to-Go TLS, same-namespace backend, per-backend CA/serverName
ServersTransport and isolation. Shared insecureSkipVerify is forbidden for this
backend. Live IdP, proxy spoof/bypass, HBA, replica promotion and restore
evidence are unrun; source/CI success does not activate this portal.

It checks exact SQLSTATE 42501 / HBA 28000 and x509 classes, SET ROLE/TRUNCATE denial,
database-clock expiry, bounded cleanup/cardinality, two app pools and a real physical

The [fixed recovery helper](../scripts/trials/portal_recovery/README.md) is hosted

substitute. A local run without `PORTAL_REQUIRE_DISPOSABLE_PROOF` skips a missing disposable

environment of the "Focused actual PostgreSQL and authorization tests" step, so

that step. The same variable on an earlier step does not reach this process.

Login starts have one constant-size per-engine limiter: burst 4, one start/second;
under a two-replica ceiling this is burst 8/two starts per second. The shared store
serializes insert admission across replicas using transaction advisory locks,
with waits bounded by the operation deadline. Each table caps at 256 rows and deletes
at most 32 expired rows per insertion, without UPDATE/admin grants. No function privilege is added: the normal runtime
role must prove EXECUTE on the advisory-lock function in disposable/live acceptance.
A held insert advisory lock does not lock logout, revoke, or callback DELETE
statements, including while an insertion is held at its pre-commit boundary.
That lock independence is not same-replica availability. The pool has two
connections, so two inserts can hold both, and a revoke on that replica then
waits for a connection until the operation deadline and can return unavailable.
The hosted overlap fixture revokes through a separate pool. Deadlines bound the
wait, and there is no retry.
These source bounds are conservative admission limits, not measured production
capacity or an SLO; deployment replicas, retention policy, real API latency and
legitimate-flow proof must be accepted before activation.

The witness GET budget (`witness-gets-per-second`, `witness-get-burst`) went
with the witness on 2026-10-26. Store operations make no Kubernetes request.
Automatic browser polling stays off. Per-client ingress limits stay a Gate A
activation input.

Focused commands: Go1.27.2, GOTOOLCHAIN=local, GOMAXPROCS=2, nice -n 19,

## Pilot agent image for one session (default off)

History binds only at a session's first launch on agentd 2.47 or later, and
every pod today runs the one templates image. A templates edit drains every
idle session. To try a newer agent image on a new session without that, the
operator takes two flags. Both are empty by default, and both or neither must
be set:

- `--pilot-agent-image` is `ghcr.io/thaynes43/dev-env:2.X.Y@sha256:<64
  lowercase hex>`. The 2.x tag and the digest are both required. The operator
  checks syntax only. The signature is checked by the publish workflow's
  cosign verify, by review of the HelmRelease line, and by the cluster's image
  audit.
- `--pilot-agent-session` is `<parent>/<key>`. The parent is the creating
  session's name, a DNS-1123 label such as `dev-env-1027-111645`: a session
  caller's `spec.parent` is its own session name. Human, client, coordinator,
  portal and standby callers record `<namespace>/<name>` parents, which this
  flag cannot select. The key is a non-empty label value. There is exactly one
  `/`.

A set pair with a bad value, or only one flag, fails operator startup.

A session runs on the pilot image when all of these hold:

- Its `spec.parent` equals the parent. The API sets that from the caller's
  authenticated identity, so only that session can create such a session.
- Its idempotency-key label equals the key. The caller sets that with
  `agent-run --idempotency-key`.
- The agent is Claude, the mode is remote or local, and the repo is `dev-env`.
- It has no workspace, no project canary and no private pilot.

The selection is not limited to one session. While the flags stay set, it
matches every session with that parent and key, for the life of each one. The
API dedupes a key only against unfinished sessions, so the same parent can
create a second matching session after the first is suspended or finished. A
session that already had that parent and key before the flags were set gets
the pilot image at its next pod. Keeping it to one session is a procedure, not
something the operator enforces:

- Choose a key that parent has never used.
- Use it for one session only.
- Remove or change the flags when the pilot ends.

Only the image of a matching session's own pod changes. The pod keeps
everything else: the templates revision label, env, args, mounts, profile,
Secrets, egress and grants. Hold pods and task-budget workers keep the
templates image. With the flags unset, every pod is built exactly as before.
The operator log line "created the session pod" names the pod's agent image,
so a match is visible there.

What this means in use:

- History needs the session's first launch to be on the pilot image. Create
  the session after the flags are set. An existing session is never rebound.
  A session that first launched on an older agentd stays without history,
  even if a later pod runs the pilot image.
- The pod carries the current templates revision. It drains only on a
  templates change, and its next pod is on the pilot image again while the
  flags stay.
- Removing the flags puts a matching session's next pod on the templates
  image. Its history is then Unavailable if the templates image predates 2.47.

Trust model: the image is pinned by digest, from the same signed repository
as the templates image, and the flags are a reviewed HelmRelease line. The
pilot changes the code version of the matching sessions. It does not change
their profile, Secrets, egress or grants. The flags select by metadata and are
not an authorization to read history; the portal action scope is still
required.

## Remote Control link in the Sessions view

The portal reader's `view=activity` summary may carry `remoteControl`:
- `state` is the word from AgentSession `status.remoteControl`, such as `registered`, `starting` or `pair-code-issued`.
- `url` is present only when it is exactly `https://claude.ai/code/session_<id>`.

The name and session id are never sent. The portal re-checks both values, and it refuses a page with a malformed entry, as it does for its other optional fields.

A registered agent with a link gets an **Open in Claude** link in its header. Every agent gets a **Remote Control** line in its context:
- Registered;
- Registered, no link reported;
- Pairing code issued (pairing not confirmed): Codex cannot see whether a phone paired;
- Starting, Login required, Offline, Not paired, or Error;
- Not reported;
- None (headless task);
- None (local terminal).

Any other state shows its own word, escaped.

This is read-only. It adds no portal action and needs no operator flag.

**Deploy the portal before the operator.** The portal rejects activity keys it does not know.

## Default-off portal launch route

The operator can let the portal reader start one constrained agent session on
behalf of a portal user. It is off unless `--portal-launch-repo=<repo>` is set.
Three flags configure it:

- `--portal-launch-repo=<repo>`: repeatable (at most 16, no duplicates), each a
  repository name as the AgentSession schema accepts.
- `--portal-launch-profile=<name>`: required whenever a repo is set. A DNS-1123
  label, it is the templates profile every launched session runs on.
- `--portal-launch-max-unfinished=<n>`: 1 to 8, default 2. The most unfinished
  portal-launched sessions at once.

Any of them needs `--enable-portal-reader`, and the profile and cap flags need
at least one repo; a missing or invalid value fails startup. With no repo flag
the route does not exist: `POST /v1/portal/sessions` answers 404, and the portal
reader still cannot create through `POST /v1/sessions`.

- **Route.** `POST /v1/portal/sessions`, for the portal reader only. Every other
  caller, including a human, a client, a session and a coordinator, is refused.
- **Request.** Strict JSON: unknown keys, duplicate keys, JSON `null` for any key,
  trailing values and a query string are refused. Fields are `requestID` and
  `actorRef` (the same opaque-ID rule as Send), `repo` (in the allowlist), `mode`
  (`task`, `local` or `remote`), `model` (a full id; an alias such as `opus` is
  refused by the rule agent-run uses), and optional `effort` and `size` (`S` or
  `M`). A task needs a `prompt`; local and remote take none. The agent is always
  `claude`.
- **What it can never set.** Project, base, profile, tools, limits, lifecycle,
  restore, canary, name and lane are not fields. The profile is the operator's
  flag.
- **One create path.** The route builds a fixed `CreateSessionRequest` and runs
  it through the same create handler as `POST /v1/sessions`, so the model,
  effort, size, prompt, profile and idempotency rules are the existing ones. It
  writes no second validator. A prompt that fits the 64 KiB limit but whose
  session document would exceed agentd's 128 KiB transport (for example 50,000
  `<` characters) is refused by that existing check with 422.
- **Parent.** `spec.parent` is `portal/<actorRef>`, which the portal shows as
  "launched by". The caller is a derived value that exists only inside this
  route: depth 1, no profile to hand on, and no other route accepts it. A parent
  equal to another configured caller's identity is refused.
- **Cap.** Inside the create lock (which is per operator replica, so launches
  racing on two replicas can exceed the cap by one each), after the
  idempotent-repeat check, the route counts the unfinished sessions (the predicate the idempotency dedupe uses) whose
  parent starts with `portal/`. At the cap it answers 429 `limit_exceeded` and
  creates nothing. The cap is across all portal users, not per user. A repeat of
  an existing request still returns its session at the cap, and a finished or
  suspended session no longer counts.
- **Idempotency.** The key is `portal-` plus 40 hex digits of the request ID's
  SHA-256. The existing per-parent dedupe applies: a repeat of the same request
  while the session is unfinished returns the same session (200), the same ID with
  a different request is a conflict (409), and a new ID starts a new session. Once
  that session has finished, the same ID starts a new one.
- **Receipt.** `requestID`, `sessionName`, `sessionUID`, `phase` and `observedAt`.
  `Pending` is expected. Errors use the existing shapes and never echo the prompt.

### Choosing the profile is Tom's activation decision

What a launched session can reach is exactly what its profile grants. The
templates' default profile, `full`, is the widest: the GitHub bot token, GCP,
Cloudflare, Proxmox-reader and Omni keys, the MCP secrets (including the UniFi
write tools), and the Claude and Codex logins. The route therefore never falls
back to it: the flag is required. For a task that runs on a portal user's
prompt, activation should name a narrower profile, such as `dev`, and Tom
confirms what that profile grants before the flag is set. `dev` still carries
the GitHub bot token and the UniFi MCP token, and it has no keeper Claude login,
so a remote launch on `dev` shows Login required until someone runs
`agent-run login`. The operator refuses `workbench` at startup, and on every request the route
resolves the profile and refuses one that names any ServiceAccount (the
workbench's carries exec rights) or that the templates no longer hold. A templates edit to
that profile changes what portal launches get, from the next pod each one
starts.
