# Portal session runtime contract (M5B, Story 178)

Source direction: PORTAL178-M5B-SESSION-RUNTIME-20261023-01, extending
DESIGN-029 and accepted M3. This document amends M3's token-discard and
UserInfo prohibition for this narrow implementation: retain one short-lived
user access token inside the exact encrypted browser session and query one
fixed HTTPS UserInfo endpoint for current authorization. Never retain a refresh
token, request offline_access, resolve a token by subject, expose credentials in
Principal/templates/errors/logs, or infer operator Human/Client authority.
M3's authentication checks, CSRF and opaque cookie rules continue to apply.

## Store and recovery boundary

Use existing Go BFF and CNPG PostgreSQL, two tables in logical database
`dev_env_v2_portal`, schema `portal`: pending_logins and sessions. Handles are
SHA256 digests only. Rows are created with INSERT only; consumption/revocation use conditional DELETE. Login consumption atomically matches handle, state digest, current
generation and expiry; incorrect state cannot consume the row. Every read is
from the writable primary, never a read replica/cache. Errors, uncertain commits,
outage, expiry or decrypt failure deny; there is no memory fallback
or automatic replay. AES-256-GCM uses a separate 32-byte server key; a fresh nonce
and authenticated row/type/version/generation/expiry/state context prevent
ciphertext swaps. Sensitive identity, access token, CSRF, state, nonce and PKCE
fields are encrypted. Polling cannot extend lifetime. The server and cookie
deadline are capped by the actual access-token deadline, with no refresh path.

**Recovery witness dropped, 2026-10-26.** Tom ruled on #178 that a PostgreSQL
restart or failover must need no human action. The portal no longer reads the
`dev-env-v2-portal-admission` ConfigMap, measures the backend incarnation, or
reads any admission input. A store transaction is `SET LOCAL synchronous_commit
= on`, the session SQL, then one COMMIT; an uncertain commit is still unavailable
and never replayed. The shared postgres16 cluster has no synchronous replica, so
an acknowledged revoke can be lost by failover or by a restore from backup, and
the revoked session then authenticates again until it expires (at most the 12h
absolute TTL). That risk is accepted. To end it, delete the session rows or
rotate `SESSION_GENERATION`; every row carries the generation in its SQL key and
AEAD context, so rotation invalidates every existing session and pending login.
DESIGN-029 records the ruling; the M6 recovery contract is superseded.

Administrator-reviewed bootstrap SQL (proposal, never run by BFF):

```sql
CREATE ROLE dev_env_v2_portal_migrator LOGIN NOINHERIT NOSUPERUSER
  NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
CREATE ROLE dev_env_v2_portal_runtime LOGIN NOINHERIT NOSUPERUSER
  NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
CREATE DATABASE dev_env_v2_portal;
REVOKE ALL ON DATABASE dev_env_v2_portal FROM PUBLIC;
GRANT CONNECT ON DATABASE dev_env_v2_portal
  TO dev_env_v2_portal_runtime, dev_env_v2_portal_migrator;
-- In dev_env_v2_portal, as administrator:
REVOKE ALL ON SCHEMA public FROM PUBLIC;
CREATE SCHEMA portal AUTHORIZATION dev_env_v2_portal_migrator;
-- Migrator creates ONLY the two tables using migrations/001_sessions.sql.
REVOKE ALL ON SCHEMA portal FROM PUBLIC;
GRANT USAGE ON SCHEMA portal TO dev_env_v2_portal_runtime;

  TO dev_env_v2_portal_runtime;

  SET search_path = pg_catalog, portal;
ALTER ROLE dev_env_v2_portal_runtime IN DATABASE dev_env_v2_portal
  SET statement_timeout = '5s';
```

Credentials must be set through reviewed secure provisioning, never SQL files,
command arguments or logs. Migrator owns only portal schema/tables, never the
database or other objects; do not grant database CREATE/TEMP or memberships.
Mount migrator only in a separately reviewed migration job. The BFF gets no
migrator/admin token, grant option, inherited/admin role, ownership, UPDATE or CREATE.
Audit effective memberships and default privileges as well as explicit grants.

PUBLIC CONNECT/TEMP on other databases cannot be cancelled by a role-local
REVOKE while PUBLIC retains them. Do **not** revoke shared PUBLIC privileges
across the cluster as a convenience. Proposed role-scoped ordered HBA rules
must precede any broad shared allow; CNPG-generated HBA ordering must be checked
in the eventual review. If that ordering cannot enforce these rejects, this
proposal is insufficient and provisioning remains held:

```text
hostssl dev_env_v2_portal dev_env_v2_portal_runtime  <reviewed-BFF-CIDR> scram-sha-256
hostssl dev_env_v2_portal dev_env_v2_portal_migrator <reviewed-job-CIDR> scram-sha-256
host all dev_env_v2_portal_runtime,dev_env_v2_portal_migrator 0.0.0.0/0 reject

local all dev_env_v2_portal_runtime,dev_env_v2_portal_migrator reject
```

These role-specific rules reject other DBs, plaintext, unmatched source addresses
and local sockets without changing shared users. Positive TLS target-DB and
negative other-DB/plaintext/schema/DDL/membership tests are required before live
approval. Network policy should further narrow BFF/job egress. TLS client must
validate postgres16 CA **and** hostname
`postgres16-rw.database.svc.cluster.local`; `sslmode=require`, skip verification
and fallback plaintext are prohibited. CA reference postgres16-ca and server
certificate postgres16-server are references, not permission to read keys.

## Current authorization and deployment holds

Require the pinned issuer, a live UserInfo response for the session's own
subject with portal_is_active=true and portal_is_admin=true, plus the fixed
local metadata allowlist. Access is by group membership, not by a pinned
subject (Tom, 2026-10-26; DESIGN-029 "Group-based access"). Authentik
2026.8.5 UserInfo evaluates provider profile mappings at request time;
introspection or old ID/access-token claims cannot substitute. The future
provider-local mapping must evaluate active status and direct membership of the
privately pinned existing Admins UUID, preserve normal sub/profile and shared
mappings, and undergo separate haynes-ops review. No UUID is in this document.
Infrastructure PR4246/4257 and actual role/provider acceptance are separately owned.
The source verifier allows only asymmetric signing algorithms; deployed Authentik
must pin the reviewed RSA signer/RS256 and leave JWE encryption disabled. HS256
and unsigned downgrade negatives do not select or provision a provider key.

Request-private session references bind authorization to the exact handle and
token. A second healthy session of the same subject cannot mask a revoked one.
No cached allow. Check before metadata fetch, validate every returned OP ID
against 120/121/122/123/178, then repeat session and live UserInfo authorization
after rendering and immediately before releasing the buffered response. Errors,
redirects, missing/malformed/wrong-typed/duplicate booleans and wrong sub deny.

Local logout needs no IdP. The code client accepts only `/application/o/token/`
on the configured issuer host, the Authentik 2026.8 token endpoint. Issuer HTTP
configuration rejects any allowlisted path with a `revoke` or `introspect`
segment. No revoke, introspection, refresh, or end-session call is added, and
logout stays a local durable DELETE. Adding `end-session` to that reject list
remains optional and is not part of this source; no new IdP call is introduced.
This pin is source configuration, not a
live provider request or a shared Authentik change. Actual IdP session deletion, disable and token revoke
must deny in live Gate A using disposable identities; cookie disappearance alone
is not immediate token revocation. Do not alter Tom's real Admins membership.
The live metadata adapter remains unavailable: only OP haynes-engineering GET
for the five IDs, and server-validated dev-agents summaries with immutable
catalog dev-env/dev-env, may later be wired. No broad helper token, session-detail
fallback, prompts, logs, streams, downloads, mutation or grants.

Fixed landing route is the dev-env/internal Attention collection. Exact TLS Host
checks remain; forwarded headers cannot establish trust. Future GitOps must use
verified Traefik-to-Go TLS, same-namespace backend, per-backend CA/serverName
ServersTransport and isolation. Shared insecureSkipVerify is forbidden for this
backend. Live IdP, proxy spoof/bypass, HBA, replica promotion and restore
evidence are unrun; source/CI success does not activate this portal.

## Dependencies and disposable evidence

Primary-source verification on 2026-10-23 selected maintained
[pgx/v5 v5.11.0](https://github.com/jackc/pgx/releases/tag/v5.11.0).
Its [go.mod](https://github.com/jackc/pgx/blob/v5.11.0/go.mod) requires Go1.25.0;
the repository's Go1.27.2 and existing x/sync and x/text satisfy that floor.
The [upstream security advisories](https://github.com/jackc/pgx/security/advisories)
were checked: this pin is above the published fixes including
GHSA-j88v-2chj-qfwx (5.9.2) and GHSA-mrww-27vc-gghv (5.5.4).
`go get` checksum verification agrees with the
[Go checksum database](https://sum.golang.org/lookup/github.com/jackc/pgx/v5@v5.11.0):
`h1:IzBBtyK9AHqf98cctWFifYSci2hgQR/cd56wB4p+ogg=`. This is a targeted
dependency check, not complete advisory or production security acceptance.
Only pgx/pool's small pgpassfile/pgservicefile/puddle dependency closure is new;
no existing module is downgraded or upgraded.

The hosted disposable suite now uses production `postgresPoolConfig`, including
verified TLS, RuntimeParams and read-write ValidateConnect, for runtime pools.
It checks exact SQLSTATE 42501 / HBA 28000 and x509 classes, SET ROLE/TRUNCATE denial,
database-clock expiry, bounded cleanup/cardinality, two app pools and a real physical
promotion whose new primary serves a replicated session until the generation rotates.
The [fixed recovery helper](../scripts/trials/portal_recovery/README.md) is hosted
only and never targets production. The required `CI - Success` directly depends
on the reusable PostgreSQL job; a separate advisory/standalone success cannot
substitute. A local run without `PORTAL_REQUIRE_DISPOSABLE_PROOF` skips a missing disposable
database or failover input. The hosted PostgreSQL job sets that variable in the
environment of the "Focused actual PostgreSQL and authorization tests" step, so
the `go test` process sees it. A missing database or failover input then fails
that step. The same variable on an earlier step does not reach this process.

Login starts have one constant-size per-engine limiter: burst 4, one start/second;
under a two-replica ceiling this is burst 8/two starts per second. The shared store
serializes insert admission across replicas using transaction advisory locks,
with waits bounded by the operation deadline. Each table caps at 256 rows and deletes
at most 32 expired rows per insertion, without UPDATE/admin grants. No function privilege is added: the normal runtime
role must prove EXECUTE on the advisory-lock function in disposable/live acceptance.
A held insert advisory lock does not lock logout, revoke, or callback DELETE
statements, including while an insertion is held at its pre-commit boundary.
That lock independence is not same-replica availability. The pool has two
connections, so two inserts can hold both, and a revoke on that replica then
waits for a connection until the operation deadline and can return unavailable.
The hosted overlap fixture revokes through a separate pool. Deadlines bound the
wait, and there is no retry.
These source bounds are conservative admission limits, not measured production
capacity or an SLO; deployment replicas, retention policy, real API latency and
legitimate-flow proof must be accepted before activation.

The witness GET budget (`witness-gets-per-second`, `witness-get-burst`) went
with the witness on 2026-10-26. Store operations make no Kubernetes request.
Automatic browser polling stays off. Per-client ingress limits stay a Gate A
activation input.

Focused commands: Go1.27.2, GOTOOLCHAIN=local, GOMAXPROCS=2, nice -n 19,
`go test -p 1 ./web/portal/...` and `go vet -p 1 ./web/portal/...`.
Hosted disposable session tests run under `-race` with the same CPU/package bounds.
No suite loops, load tests or local container builds. Root journal1091 narrows
runtime SQL rights to SELECT/INSERT/DELETE; no UPDATE or Touch path exists.
INSERT collisions cannot replace existing rows. Live role, DB/auth,
shared Authentik secret-safe logging, proxy/isolation and Gate A remain held.

## Default-off portal action source configuration

Source may optionally read `config/session-actions.json` under the existing
portal root. Absence leaves send and private history disabled. The object may
contain `send` and/or `history`; each is independently scoped with exact
`issuer`, `subject`, and a nonempty `targets` array of `{ "name", "uid" }`.
The issuer must match the existing pinned issuer. Invalid, duplicate, ambiguous,
or unknown fields and duplicate target names or UIDs fail closed. This scope
is additional to current session, UserInfo and group authorization; metadata
access does not grant either action. The existing operator token and pinned CA
are reused. Do not populate this file with real identities or targets without
separate authorization.

Operator source separately accepts repeatable `--portal-send-target=name=uid`
and `--portal-history-target=name=uid` options. Each action has its own target
map; neither is enabled by `--enable-portal-reader` alone. Explicit targets
require that reader flag, and invalid or duplicate entries fail startup. These
source interfaces are not an installation or approval: deployment, eligible
idle agentd rollout, provider format qualification, live private access and
send proof remain separate prerequisites. Legacy unbound history and agentd
versions lacking the conversation control remain unavailable.
