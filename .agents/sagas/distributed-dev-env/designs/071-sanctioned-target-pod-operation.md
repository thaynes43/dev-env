- **Status: Draft**
- **Date:** 2026-11-21
- **Tracking:** [OP943](https://work.haynesnetwork.com/work_packages/943), slice 1. Scope comes from the revised story and OP926 journal 9510.

## 1. Scope and proposed execution route

Authorize one typed operation for one already selected Pod in the operator's own managed cluster. An ordinary session needs one explicit owner approval in Asks. A named existing designated superuser can initiate its own operation under its existing workbench-by-creation authority, within an explicit session and target designation. Both paths use the same immutable request, final checks, one-use fence and receipt. A worker or child always authenticates as itself.

The first action is `ha.config.validate/v1`. Its only candidate is a purpose-built, non-serving sandbox Pod named `op943-ha-sandbox` in the existing `home-automation` namespace. The name is proposed for the fixture. The target container is `app`. Its immutable synthetic config comes from the proposed ConfigMap `op943-ha-sandbox-config` and is mounted read-only. The standalone sandbox Pod uses `restartPolicy: Never` and no per-container restart rules. Its protected app image, mounts and Pod spec stay fixed for that UID. The fixture has no production data, PVC, credentials, Service, public route or network access. The production HA HelmRelease in haynes-ops mounts shared persistent config and refers to credential sources. That workload is ineligible. No live HA data was inspected.

**Proposed delivery:** the existing broker performs a single named `PATCH` on the fixture Pod's `pods/ephemeralcontainers` subresource. Kubernetes appends one fixed, digest-pinned validator. A fail-closed admission rule permits only the complete server-derived shape for a reserved operation against the exact existing Pod UID. There is no `targetContainerName` process-namespace join. The binding to `app` means the helper can read only the exact fixture volume and config revision mounted by that named container. The helper uses a built-in validator on a fixed schema and file set. It accepts no program, arguments chosen by the caller, arbitrary paths, network destinations or credentials. It reports a bounded completion summary in its own termination message. The broker reads this from the same named Pod. Kubernetes documents the [append-only subresource and ephemeral container constraints](https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/#EphemeralContainer) and [name-scoped subresource RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#referring-to-resources).

This is a proposed use of a standard Kubernetes API, with a material new code-execution permission for the broker. The named RBAC rule alone permits arbitrary ephemeral container shape at that name. Runtime remains disabled unless separately reviewed policy makes the complete shape, grant binding and fixture isolation mandatory. If the existing admission stack cannot enforce those invariants for the exact subresource, stop. Keep every existing guard in force. Use neither Kubernetes exec or proxy, the HA code editor or HTTP API, nor a generic maintenance executor as a fallback. The slice 2 acceptance harness uses local fake clients and synthetic objects only.

## 3. Custody, revocation and execution

1. **Admit the request.** Extend `POST /v1/grants` with a `target-pod-operation` AccessGrant variant. Validate the exact tuple, live actor, fixed deadline, schema and trusted single-target catalog before creating the immutable request. Require supported schema and a read-back of all critical fields. Require a stable submission ID. Use a deterministic grant name scoped to the exact actor and submission ID. Create it at most once. On a name collision, read back that one grant and accept only the same actor and scope. A changed scope refuses, and losing the create response cannot generate another grant. Use existing GET routes for status. Requests that fail admission create no Ask or executable work.
2. **Record the decision.** For ordinary authority, reuse the existing broker grant Ask path and `Decide` recheck. Add the type to the existing tag validation and the exact card rendering. Require a protected broker origin and exact owner principal. For standing authority, the broker records the verified designation and actor as the decision provenance. Select the path from server authority, before any policy matching. Keep the existing generic `--enable-grant-asks` off for the sandbox. A new default-off setting for this type alone gates its new requests and broker processing.
3. **Consume exactly once.** Before execution, use uncached reads of the grant, original Ask or standing designation, caller Session/pod and target Pod. Refuse missing, forbidden, incomplete or conflicting evidence. Check `spec.release`, deletion, deadlines, authority, health, immutable volume, identity, exact action and local executor availability. The broker alone uses a resourceVersion-conditional status update to change approved and unused to reserved, with a server-derived operation ID, digest, decision reference and sequence. Release and reservation conflict on the same grant version. Only the writer that received a successful reservation response may dispatch, after verifying the reservation survived schema pruning. A conflict permits fresh evaluation of an unused record. A timeout or process loss at or after reservation burns the attempt. Another reconcile may read back evidence. It cannot dispatch a reserved operation. An old broker must fail closed on the new variant before any schema or flag rollout.
4. **Admit delivery.** Re-read grant and target immediately before the one patch. The patch has Pod UID and resourceVersion preconditions and appends exactly one deterministically named helper to an empty ephemeral container list. One helper per sandbox Pod incarnation also prevents two different grants from racing into the same fixture. Existing entries and any other spec or metadata differences refuse. Match at admission on `UPDATE pods/ephemeralcontainers` and verify the broker identity, exact permitted fixture Pod, complete old/new diff, expected grant type, UID, reserved operation ID and digest, live unreleased state and deadline. For the ordinary path, independently verify the bound, affirmative owner Ask via live read, including its UID, origin, requester, digest and owner principal. The standing path requires the authenticated operator's immutable binding to the named workbench-by-creation designation and a matching current designation in protected admission configuration. The broker independently rechecks live session eligibility. A lookup failure or absent admission gate blocks delivery. Require the original container identity in the old Pod status, fixture readiness and trusted config. Disable mutating transport retries. Never retry a patch after sending it, including on conflict, response loss or replica failover. Read only the established operation and exact Pod.
5. **Run and collect.** The tokenless helper checks Downward API Pod name, namespace and UID, the pinned immutable fixture digest and absolute deadline before reading config. It refuses if it cannot finish within its fixed run budget. Use a non-root, read-only-root filesystem image, dropped capabilities, no privilege escalation, RuntimeDefault seccomp, no shared process namespace, no host mounts/devices, no service-account projection, no envFrom, no TTY and no listeners. Mount only the synthetic config read-only. Bound work, bytes read, output and runtime within the sandbox Pod's predeclared headroom. Ephemeral containers cannot specify separate resource requests and limits. Verify the original app container remains Ready with the same container ID on collection. A change or exit across the delivery window disqualifies the result. The validator can only touch the immutable synthetic projection in that window.
6. **Revoke and expire.** Reuse `DELETE /v1/grants/{name}` for requester release. Add an owner-only take-back action on the existing portal grant card, using the same authenticated principal and a UID/digest-conditional `spec.release` update. A withdrawn Ask, lost designation, session end or elapsed deadline invalidates unused work. Release before reservation wins the CAS. A release seen before Pod admission blocks the patch. Once reserved, take-back reports an in-flight outcome until evidence resolves whether admission won. Kubernetes does not transact the grant and Pod writes together or cancel an accepted append. The helper enforces the absolute deadline at start and while running. An in-flight sandbox check reads only immutable synthetic data. A mutation that requires revocation enforcement closer to its side effect needs a reviewed backend with that property. No mutation is enabled here.

### Receipt and ambiguity

Keep the terminal receipt in the retained AccessGrant status. Use explicit `reserved`, `confirmed`, `refused` and `unconfirmed` operation states within the existing grant lifecycle. Use a new grant-specific schema field, set-once reservation, write-once outcome and broker-only conditional updates. The canonical receipt includes schema version, grant UID, operation ID and scope digest, bound actor and target, recorded approval path and Ask UID or designation reference, deadlines, reservation and observation times, before/after digests where applicable, helper image and container ID, verdict, and a fixed reason code. Record the canonical receipt digest and correlate it with protected Kubernetes audit evidence for the grant status and subresource writes using object UID and operation ID. Keep raw config, answer text, private actor IDs and addresses out of returned receipts and logs.

A success requires a same-UID Pod read, the exact admitted helper spec, a matching terminated container and image identity, schema-valid termination message, matching operation/target/config digests, expected exit code and timing, retained grant outcome and consistent audit evidence. Pod status is written by kubelet under normal node authorization. Sessions and fixture containers have no write path to it or the retained receipt. A digest detects changes only when compared with an independent protected record. Tamper resistance relies on trusted admission, API server, kubelet, broker and independently retained audit evidence. Audit sink availability, access/retention and correlation for these verbs need separate proof before activation. Publish only `unconfirmed` if an acknowledged fence, outcome write or required evidence cannot be proved. Preserve the reservation, stop, and require review of the original evidence before any new request. No attempt auto-retries, follows a replacement Pod, rolls back or restarts.

## 4. Preflight, backup, restore and restart

- **Sandbox validation:** check the fixed config tree and SHA-256 before validation. Refuse unexpected files, symlinks, oversized inputs, external includes, credential directives or inconsistent content. Start and finish against the same fixture revision. Return only bounded validation counts and fixed status codes. The dry-run acceptance plan covers both a valid fixture and a deliberately invalid fixture. No backup is needed for a read-only check. The ephemeral container record persists on the same Pod and the broker has no permission to delete it or the Pod.
- **Future apply and restore:** review each typed action and its backend before adding it to the action catalog. Pin the exact content digest, expected live revision and authorized change. Preflight validates a staged copy off the active path, checks free space and writable scope, and records a verified backup and checksum in protected workload-owned storage. Hold a single-writer lock across final compare, durable atomic replacement and immediate read-back. Preserve before/after hashes and backup reference. Ambiguous effect freezes the target for diagnosis. Restore is a separately authorized typed action against the same target, backup digest and observed current revision, followed by read-back. Refuse any file set or deployment that cannot meet those bounds. No write-capable backend, volume or RBAC is proposed for this slice.
- **Restart:** a distinct future `pod.restart/v1` request needs fresh exact owner approval, including for a standing initiator. Require the prior confirmed receipt, its target UID and config digest, known controller ownership, healthy preflight, verified restore point and an authorized window. Use a separately reviewed executor with UID/resourceVersion-conditional deletion of only that Pod. A successor is observed independently for readiness and may not inherit the old grant. Any missing precondition or unclear outcome stops. Neither validate, apply, restore, expiry nor release can trigger restart. This draft grants no restart permission.

## 6. Threat model

| Threat | Control and residual |
| --- | --- |
| A confused or malicious session changes UID, namespace, cluster, container, content, action or deadline | Immutable versioned digest, exact owner preview, live actor/target reads and final Pod UID/resourceVersion preconditions. Replaced, moved or restarted target is ineligible. Content is never interpolated as code. |
| Forged consent or authority laundering | TokenReview and live Session/Pod/SA binding. Only protected portal answer bound to owner issuer/subject or the exact standing designation. Broker can't write approval answers. General Ask, agent chat, policies or child inheritance give no authorization. |
| Replay, two replicas, timeout or crash | Durable grant CAS, exact preconditions, one-helper occupancy on the target and no retry after a send. Grant and Pod use distinct writes. Unknown membership or delivery is an explicit terminal hold on reuse. |
| Broker becomes a general launcher or broadens access through a different resource | Named subresource permission plus fail-closed exact-shape admission, scoped lookup and protected GitOps. Existing policy must admit the restricted helper as is. A compromised broker can cause denial of service and has pre-existing rights outside this route. It cannot derive an owner answer from its own identity, create one through its Ask rights or substitute a different scope at admission. |
| Fixture access through another agent path or sibling | Exact protected Pod/config provisioning, synthetic read-only data, fixed image, restricted security context, no shared PID, no token, no Service and deny-all networking. Policy must cover direct Pod access, controller and alternate creation/mutation, including use of legacy agent identities. Pod UID alone does not make arbitrary workloads safe. |
| Misleading receipt, missing evidence or compromised trust root | Protected set-once state, same-UID kubelet evidence, canonical digest and independent API audit correlation. No result turns into authority. Cluster-admin, node/kubelet, trusted image or GitOps root compromise lies outside this guarantee. Missing, stale or inconsistent evidence yields unconfirmed and no follow-on action. |
| Resource exhaustion, config leakage or irreversible effect | Cap requests, fixed validation budget, small synthetic input, bounded outputs and no live config. Read-only fixture avoids persistent side effects. Separate reviewed apply, restore and restart gates own future effects. |

## 8. Offline fixture specification for slice 2

All fixtures use synthetic objects and a fake clock, approval store, admission boundary and executor. Assert externally visible state, receipt and exact number of backend calls. Exercise actual schema and admission evaluation offline where possible.

| Fixture | Required result |
| --- | --- |
| Ordinary requester, affirmative owner Ask, exact tuple and valid fixture | One reservation, one admitted append, read-only validation and one confirmed receipt. |
| Named existing workbench-by-creation session with exact target designation | One operation and receipt with standing provenance. No Ask needed for validator. |
| No Ask, unanswered Ask, negative, withdrawn, generic, foreign, recreated or forged Ask, or a non-owner answer | No dispatch. A role or display name masquerading as the owner fails. |
| Different cluster, namespace, Pod name, Pod UID, container, image/container ID, action, fixture digest, input or deadline | Denied for each independent mutation. No target lookup by selector or name fallback. |
| Deadline reached, revoked, released, disabled flag, lost standing designation, or stale requester identity | No dispatch. Exercise both before approval and after approval before reservation. |
| Workload moved or recreated after approval, or replacement between check and patch | Old operation denied or definitively refused by preconditions. New Pod remains untouched. Container restart during verification cannot yield confirmed success. |
| Same grant invoked twice, concurrent replicas, or two grants for one fresh sandbox | At most one append. Replay reads the existing receipt. Losing grant cannot use the occupied Pod. |
| Release CAS racing reservation, and release before/after admission | Release before reservation wins or live admission sees it and refuses. Accepted in-flight validation stays bounded and is never repeated. |
| Missing schema field, unavailable admission, timeout, stale/ambiguous read, UID mismatch on read-back | No pre-dispatch side effect. After reservation, only original evidence can resolve the outcome, with no re-dispatch. |
| Crash or response loss before or after the patch, conflicting or forged status, missing termination message/audit | Keep one-use fence, report unconfirmed unless authentic evidence resolves it, and never restart or restore automatically. |
| Unauthorized submitter, raised/child or replacement workbench session, untrusted labels, policy/delegate/attestation attempt | Cannot qualify under standing authority or replace explicit owner approval. |
| Direct fixture exec, attach, proxy, port-forward, delete, status/spec edit, or malformed ephemeral append | Admission or RBAC denies. Check other names/namespaces and differing image, mounts, flags, privilege, token, command and append count. |
| Malformed or malicious synthetic config, symlink, external include, changed digest, runtime overrun | Bounded refusal, no writes, no contents in receipt and no follow-on action. |
| Apply, restore or restart requested through validation or with old approval | No dispatch. Future restart fixture requires distinct exact owner consent and a matching confirmed prior receipt. |
